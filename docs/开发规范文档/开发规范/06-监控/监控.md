# 监控

> 目标：上线后看得见——掌握智能体服务的运行状态监控面、业务指标采集与问题定位路径。

## 监控对象总览

| 监控对象       | 观测手段                                       | 关注点                             |
| -------------- | ---------------------------------------------- | ---------------------------------- |
| 智能体运行     | 事件流（SSE）+ OTel 三层 span + 业务指标       | 回复耗时、模型调用次数、token 消耗 |
| 模型成本      | `ReplyBudgetControlMiddleware` + `usage`        | 加权 token 预算、超额终止          |
| 工作区         | WorkspaceManager 行为                           | 缓存驱逐、后端创建延迟             |
| 会话           | SSE 回放 + `GET /sessions/{id}`                 | 会话堆积、异常中断                 |

## OpenTelemetry 可观测性底座（已集成）

> 智能体服务已内置 OpenTelemetry 观测能力：追踪（TracingMiddleware）、指标（Metrics API）、日志（结构化日志关联 trace_id）三信号齐备，配置 exporter 即可接入任意兼容 OTel 的观测后端，无需改造业务代码。

### 三信号现状

| 信号    | 状态   | 产出                                                                 |
| ------- | ------ | -------------------------------------------------------------------- |
| Traces  | 已集成 | `TracingMiddleware` 三层 span，遵循 OTel GenAI 语义约定               |
| Metrics | 已集成 | OTel Metrics API 埋点，指标按本节清单命名上报                         |
| Logs    | 已集成 | 结构化日志携带 `trace_id`，与 span 双向关联                           |

### 数据模型：span 与指标

**Traces——三层 span**（接入细节见 [tracing 日志](tracing日志.md)）：

```text
invoke_agent（整轮回复，含 reply_id、HITL/外部执行等扩展属性）
 ├── chat（模型调用，含 gen_ai.usage.* token 属性）
 └── execute_tool（工具执行，含工具名与结果）
```

span 属性分两类：

- **标准 GenAI 属性**：`gen_ai.operation.name`、`gen_ai.agent.name`、`gen_ai.request.model`、`gen_ai.usage.input_tokens`/`output_tokens`、`gen_ai.conversation_id`——遵循语义约定，主流观测后端可直接识别；
- **agentscope 扩展属性**：`agentscope.agent.reply_id`、`agentscope.agent.hitl_pending_tools`、`agentscope.agent.external_execution_pending_tools`、`agentscope.usage.cache_input_tokens`——按业务维度过滤时使用。

**Metrics——统一指标清单**（`agent.` 前缀；Histogram 自动产出 `_sum`/`_count`/`_bucket` 后缀）：

| 指标名                  | 类型      | 语义                                  | 采集点                        |
| ----------------------- | --------- | ------------------------------------- | ----------------------------- |
| `agent.reply.duration`  | Histogram | 单轮回复耗时（秒）                    | `on_reply_start`              |
| `agent.reply.errors`    | Counter   | 回复失败数                            | `on_reply_start`              |
| `agent.reasoning.steps` | Histogram | 推理步数（ReAct 迭代深度）            | `on_reasoning`                |
| `agent.model.calls`     | Counter   | 模型调用次数                          | `on_model_call`               |
| `agent.model.tokens`    | Histogram | 单次调用 token 用量（输入/输出/缓存） | `on_model_call`               |
| `agent.tool.calls`      | Counter   | 工具调用次数（按工具名）              | `on_acting`                   |
| `agent.tool.errors`     | Counter   | 工具执行失败数                        | `on_acting`                   |
| `agent.budget.exceeded` | Counter   | 预算超额优雅终止次数                  | ReplyBudgetControlMiddleware |

所有指标建议携带维度 `agent.name`、`session_id`、`model`，便于按智能体/会话/模型聚合；会话级视角直接用 span 的 `gen_ai.conversation_id` 聚合，无需单独指标。基于以上指标可直接配置告警（回复失败率、P95 耗时、预算超额次数、工具失败率超阈值报警）。

### 使用方式

**第一步：三信号统一初始化**（应用启动时执行一次）：

```python
from opentelemetry import metrics, trace
from opentelemetry.exporter.otlp.proto.grpc.metric_exporter import OTLPMetricExporter
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.metrics import MeterProvider
from opentelemetry.sdk.metrics.export import PeriodicExportingMetricReader
from opentelemetry.sdk.resources import Resource
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor

resource = Resource.create({"service.name": "my-agent-service"})

# Traces：三层 span 由此导出
provider = TracerProvider(resource=resource)
provider.add_span_processor(
    BatchSpanProcessor(OTLPSpanExporter(endpoint="otel-collector:4317"))
)
trace.set_tracer_provider(provider)

# Metrics：按周期批量导出
metrics.set_meter_provider(
    MeterProvider(
        resource=resource,
        metric_readers=[
            PeriodicExportingMetricReader(
                OTLPMetricExporter(endpoint="otel-collector:4317")
            )
        ],
    )
)
```

**第二步：装配中间件**（追踪放首位，保证覆盖整轮回复）：

```python
agent = Agent(
    ...,
    middlewares=[
        TracingMiddleware(),      # 最外层：三层 span
        MetricsMiddleware(...),   # 业务指标埋点（见下节示例）
        ReplyBudgetControlMiddleware(...),
    ],
)
```

**第三步：后端地址用标准环境变量配置**（无需改代码）：

| 环境变量                      | 默认值                   | 说明                                     |
| ----------------------------- | ------------------------ | ---------------------------------------- |
| `OTEL_SERVICE_NAME`           | -                        | 服务名，观测后端的数据源标识             |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://localhost:4317`  | OTel Collector 地址（gRPC）              |
| `OTEL_TRACES_SAMPLER`         | `parentbased_always_on`  | 采样器，生产建议 `parentbased_traceidratio` |
| `OTEL_TRACES_SAMPLER_ARG`     | -                        | 采样比例，如 `0.1`                       |

> **提示**：`TracingMiddleware` 未配置真实 SDK 时零开销短路（不产生 span）——本地开发不初始化也不影响功能。

### 指标采集方式（三选一，可叠加）

1. **span 派生指标（零代码）**：Collector 上启用 `spanmetrics` connector，从三层 span 自动聚合延迟/错误/吞吐；
2. **中间件业务指标（推荐）**：钩子内调用 OTel Metrics API 埋点（见下一节示例），覆盖回复耗时、token、工具调用等业务指标；
3. **基础设施指标**：进程/运行时指标（CPU、内存、GC）由 OTel 采集器上报，与业务指标同链路。

### 部署形态

```text
智能体服务 ──OTLP gRPC──> OTel Collector ──┬──> Jaeger / Tempo / SigNoz（追踪）
                                           ├──> Prometheus / VictoriaMetrics（指标）
                                           └──> Loki / Elasticsearch（日志）
```

也可一体化：Collector 直连 SigNoz 或 Grafana（Tempo + Prometheus + Loki）全家桶，面板开箱即用。

### 日志关联与排查

结构化日志经 `LoggingHandler` 上报后自动携带 `trace_id`/`span_id`——从慢 span 可跳转关联日志，从日志可反查链路：

```python
import logging

from opentelemetry.exporter.otlp.proto.grpc._log_exporter import OTLPLogExporter
from opentelemetry.sdk._logs import LoggingHandler, LoggerProvider
from opentelemetry.sdk._logs.export import BatchLogRecordProcessor

log_provider = LoggerProvider(resource=resource)
log_provider.add_log_record_processor(
    BatchLogRecordProcessor(OTLPLogExporter(endpoint="otel-collector:4317"))
)
logging.getLogger().addHandler(LoggingHandler(provider=log_provider))
```

### 采样策略

| 环境             | 配置                                      | 说明                          |
| ---------------- | ----------------------------------------- | ----------------------------- |
| 开发/测试        | 默认全量                                  | 完整链路便于定位              |
| 生产（低流量）   | `parentbased_traceidratio=1.0`            | 全量采，成本可承受时          |
| 生产（高流量）   | `parentbased_traceidratio=0.1` + 尾部采样 | 默认 10%，Collector 保留错误/慢 span |

> **注意**：采样只影响 span（成本大头在追踪侧）；指标为聚合值、日志按需记录，均不受采样影响。

## 业务指标采集：自定义中间件

中间件是采集业务指标的正规位置（见 [中间件](../02-agentscope官方参考文档/02-核心概念/中间件.md)）——不侵入智能体与模型代码：

```python
from opentelemetry import metrics

from agentscope.middleware import AgentMiddlewareBase

meter = metrics.get_meter("agent-monitor")
reply_duration = meter.create_histogram(
    "agent.reply.duration", unit="s", description="单轮回复耗时"
)
reply_errors = meter.create_counter("agent.reply.errors", description="回复失败数")
model_calls = meter.create_counter("agent.model.calls", description="模型调用次数")


class MetricsMiddleware(AgentMiddlewareBase):
    """统计每轮回复耗时、失败数与模型调用次数，经 OTel Metrics 上报。"""

    async def on_reply_start(self, agent, state, call_next):
        import time
        state.metadata = {**state.metadata, "_t0": time.monotonic(), "_calls": 0}
        result = await call_next(agent, state)
        elapsed = time.monotonic() - state.metadata["_t0"]
        attrs = {"agent.name": agent.name, "session_id": agent.state.session_id}
        reply_duration.record(elapsed, attributes=attrs)
        model_calls.add(state.metadata["_calls"], attributes=attrs)
        return result

    async def on_model_call(self, model, messages, config, call_next):
        state.metadata["_calls"] += 1
        return await call_next(model, messages, config)
```

常用采集点：

| 钩子              | 采集指标（对应底座清单）                          |
| ----------------- | ------------------------------------------------- |
| `on_reply_start`  | `agent.reply.duration`、`agent.reply.errors`      |
| `on_reasoning`    | `agent.reasoning.steps`                           |
| `on_acting`       | `agent.tool.calls`、`agent.tool.errors`           |
| `on_model_call`   | `agent.model.calls`、`agent.model.tokens`         |

## 成本护栏：token 预算

`ReplyBudgetControlMiddleware` 在每次模型调用后累计加权成本，**超过预算立即优雅终止回复**：

```python
from agentscope.middleware import ReplyBudgetControlMiddleware

middleware = ReplyBudgetControlMiddleware(
    max_budget=200_000,          # 加权 token 总预算
    input_token_weight=1.0,      # 输入 token 权重（缓存输入可设更低）
    output_token_weight=2.0,     # 输出 token 权重
)
```

计费公式：`cost = input_token_weight × input_tokens + output_token_weight × output_tokens`。该中间件无状态、跨智能体可复用同一实例。

> **提示**：`Msg.usage` 携带本轮 token 消耗；`finished_at - created_at` 即回复总耗时——服务化场景把二者写入指标，是成本监控的最小实现。

## 运行状态监控面

### 工作区生命周期

WorkspaceManager 缓存已创建的工作区，最后一次访问 `ttl` 秒（默认 3600）后驱逐；沙箱类 manager 每 `sweep_interval` 秒跑后台 sweeper。关注点：**get_workspace 缓存 miss 率**（后端创建慢）与**驱逐风暴**（ttl 过短导致反复重建）。

### 会话与事件流

- SSE 订阅**先回放缓冲历史再接实时事件**——回放事件可作为会话审计日志来源；
- `POST /sessions/{id}/interrupt` 可外部取消运行中或 HITL 暂停的回复——卡死会话的处置手段；
- 分布式部署下同一会话同一时刻只允许一个节点处理，会话锁由消息总线保证。

## 本地调试：控制台

终端快速测试、验证智能体，无需 Web 服务：

```python
from agentscope.console import launch_console

# 进入终端对话，输入 exit/quit 或按 Ctrl+D 退出
await launch_console(agent)
```

| 环节       | 行为                                                                 |
| ---------- | -------------------------------------------------------------------- |
| 消息输入   | 以 `user>` 提示符读取输入，`exit`/`quit`/Ctrl+D 退出                  |
| 流式渲染   | 回复文本与思考过程实时打印，工具调用与结果整块输出                    |
| 工具确认   | `y` 允许一次；`a` 允许并接受建议权限规则（后续不再询问）；其余拒绝    |
| 中断       | 流式输出中 Ctrl+C 中断当前回复；确认提示处 Ctrl+C 终止本轮            |

参数：`agent`、`user_name`、`verbosity`（`quiet`/`default`/`debug`）、`max_tool_result_lines`（默认 20，`None` 不截断）。

> **注意**：`launch_console` 不含会话管理与持久化——状态随进程退出而消失。需要多用户、多会话、持久化时用智能体服务。

## 排查路径速查

```text
回复异常/超时？
├── 看事件流（SSE / 控制台 debug 档）      → 定位卡在哪个环节（推理/工具/确认）
├── 看 OTel span（invoke_agent / chat）    → 模型调用耗时与次数，取 trace_id
├── 按 trace_id 关联结构化日志             → 定位具体报错
└── 看工作区后端日志                       → 工具执行是否卡住
```

全链路追踪与日志的接入细节见 [tracing 日志](tracing日志.md)。
