# 02-核心概念

> 本篇讲清 BocomAgentScope 的 4 个核心概念，帮助你建立整体心智模型。
> 它们之间是层层递进的关系：**中间件**给智能体加能力 → **控制台**让你在终端快速调试 → **消息与事件**是智能体之间、以及前后端之间传递数据的两种形态 → **计划模式**让智能体把复杂任务拆成可追踪的清单。

| 概念 | 一句话 | 你会在什么时候用到 |
| --- | --- | --- |
| 中间件 | 不改动智能体代码，在关键位置插入日志、限流、语音、记忆等逻辑 | 想统一加横切能力（可观测、合规、成本）时 |
| 控制台 | 不启 Web 服务，直接在终端和智能体对话、看事件流 | 本地开发、快速验证智能体行为 |
| 消息与事件 | `Msg` 是完整的「气泡」，`Event` 是流式「打字机」逐块吐出的增量 | 做前端渲染、对接流式接口、持久化 |
| 计划模式 | 内置 4 个工具，让智能体用「任务清单」而非自由发挥来推进复杂工作 | 多步、长链路、需要可追踪进度的任务 |

## 一、中间件（Middleware）—— 给智能体「加挂件」

### 这是什么

中间件让你**在不修改智能体或模型源码的前提下**，往智能体运行的某些关键位置「挂」上自己的逻辑：日志、链路追踪、访问控制、预算控制、语音合成、长期记忆、RAG…… 都可以做成中间件。

框架暴露了 6 个 hook 位置（外加一个可选的工具来源 hook），覆盖从最外层 `reply` 一直到最底层模型 API 调用的整条链路：

| 位置 | 类型 | 它在哪一层、干什么 |
| --- | --- | --- |
| `on_reply` | Onion | 包裹一次完整的 reply（含所有 ReAct 轮次、工具调用、最终输出） |
| `on_reasoning` | Onion | 包裹一轮 ReAct 中的「推理」步骤（组输入 → 调模型 → 流式解码） |
| `on_acting` | Onion | 包裹一次工具调用的执行 |
| `on_model_call` | Onion | 包裹一次底层 `ChatModel` API 调用（最贴近模型） |
| `on_compress_context` | Onion | 包裹上下文压缩判定（每轮推理前可能触发） |
| `on_system_prompt` | Transformer | 每次组装 system prompt 时触发，多个中间件串行改写 |
| `list_tools` | Tool source | 可选，贡献工具列表；**不会被自动调用**，需调用方自行收集 |

> 三类 hook 的区别，一句话就够：
> - **Onion（洋葱式）**：像包洋葱一样一层层裹住下一层，能在它「前后」插逻辑、看中间事件流。
> - **Transformer（变换式）**：像流水线，前一个的输出是后一个的输入（只用于 `on_system_prompt`）。
> - **Tool source（工具来源）**：不在运行时路径上，只是声明「我这个中间件能贡献哪些工具」。

嵌套关系（越往外越先执行、越晚结束）：

```
on_reply
 └─ 每轮 ReAct：
     ├─ on_compress_context        （上下文压缩判定）
     ├─ on_reasoning
     │   ├─ on_system_prompt       （组装 system prompt）
     │   └─ on_model_call          （模型 API 调用）
     └─ on_acting                  （本轮每个工具调用一次）
```

### 怎么用

把一组 hook 写在一个类里（同一个类可同时实现任意子集），把**实例**传给 `Agent(middlewares=[...])` 即可。构造时智能体会扫描实例，按它实际实现了哪些 hook 分配到对应位置；没实现的自动跳过，零开销。

```python
from bocomagentscope.agent import Agent
from bocomagentscope.middleware import TracingMiddleware

agent = Agent(
    name="assistant",
    system_prompt="You are a helpful assistant.",
    model=model,
    toolkit=toolkit,
    middlewares=[TracingMiddleware()],
)
```

### 内置中间件速览

| 场景 | 实现类 | 作用 |
| --- | --- | --- |
| 链路追踪 | `TracingMiddleware` | 接入 OpenTelemetry，覆盖 reply / model_call / acting 三层 span |
| 预算控制 | `ReplyBudgetControlMiddleware` | 限制单次 reply 的加权 token 成本，超限即收尾 |
| 语音生成 | `TTSMiddleware` | 拦截文本输出并合成语音，注入音频事件流 |
| 长期记忆 | `AgenticMemoryMiddleware` / `Mem0Middleware` | 跨会话的长期记忆（详见 `05-上下文管理.md`） |
| RAG | `RAGMiddleware` | 推理时访问外部知识库（详见 `05-上下文管理.md`） |

> 想看某个内置中间件的完整参数与示例，可回看原始文档；上表只帮你快速选型。

### 自己写一个（最小可用）

继承 `MiddlewareBase`，实现需要的 hook。每个 onion hook 都会收到 `input_kwargs`（流入下一层的字段），通过 `next_handler(**input_kwargs)` 透传，也可覆写其中某些字段：

```python
from bocomagentscope.agent import Agent
from bocomagentscope.middleware import MiddlewareBase

class LoggingMiddleware(MiddlewareBase):
    async def on_reply(self, agent, input_kwargs, next_handler):
        print(f"[reply] start: {agent.name}")
        async for item in next_handler(**input_kwargs):
            yield item
        print(f"[reply] end: {agent.name}")

agent = Agent(
    name="assistant",
    system_prompt="You are a helpful assistant.",
    model=model,
    toolkit=toolkit,
    middlewares=[LoggingMiddleware()],
)
```

几个实用的小例子（都是真实可跑的）：

```python
import time, asyncio
from bocomagentscope.middleware import MiddlewareBase

# 计时：统计每次模型调用耗时
class TimingMiddleware(MiddlewareBase):
    async def on_model_call(self, agent, input_kwargs, next_handler):
        start = time.time()
        result = await next_handler()
        print(f"[timing] {input_kwargs['current_model'].model}: {time.time()-start:.2f}s")
        return result

# 限速：两次模型调用之间强制最小间隔
class RateLimitMiddleware(MiddlewareBase):
    def __init__(self, min_interval=1.0):
        self._last, self._min = 0.0, min_interval
    async def on_model_call(self, agent, input_kwargs, next_handler):
        wait = self._min - (time.time() - self._last)
        if wait > 0:
            await asyncio.sleep(wait)
        self._last = time.time()
        return await next_handler()

# 模型回退：主模型报错就切备用模型
class ModelFallbackMiddleware(MiddlewareBase):
    def __init__(self, fallback_model):
        self._fallback = fallback_model
    async def on_model_call(self, agent, input_kwargs, next_handler):
        try:
            return await next_handler()
        except Exception as e:
            print(f"primary failed: {e}, switch to fallback")
            return await next_handler(current_model=self._fallback)
```

### 执行顺序（记住一句）

- **Onion 类**：列表里第一个中间件在**最外层**（`mw1 前 → mw2 前 → 内部 → mw2 后 → mw1 后`）；对产生事件的 hook，内层先看到每个事件。
- **Transformer 类（`on_system_prompt`）**：从左到右接力（`原始 → mw1 → mw2 → 最终`）。

## 二、控制台（Console）—— 终端里快速调试

### 这是什么

开发时想快速验证一个智能体，**不想起 Web 服务、也不想自己手动消费几十种事件**？用 `bocomagentscope.console` 就行：直接在终端和智能体对话、实时看事件流。

它提供两个接口：

| 接口 | 适用场景 |
| --- | --- |
| `launch_console` | 和单个智能体**交互式**对话：内置输入循环、工具确认、中断处理，几乎零界面代码 |
| `ConsoleRenderer` | 嵌入**你自己的代码**：只负责把事件流渲染成终端输出，输入与编排由你掌控 |

### 启动交互对话

`launch_console` 接管终端交互的全部环节：

```python
import asyncio, os
from bocomagentscope.agent import Agent
from bocomagentscope.console import launch_console
from bocomagentscope.credential import DashScopeCredential
from bocomagentscope.model import DashScopeChatModel
from bocomagentscope.tool import Bash, Read, Toolkit, Write

async def main():
    agent = Agent(
        name="Friday",
        system_prompt="You're a helpful assistant named Friday.",
        model=DashScopeChatModel(
            credential=DashScopeCredential(api_key=os.environ["DASHSCOPE_API_KEY"]),
            model="qwen3.7-max",
        ),
        toolkit=Toolkit(tools=[Bash(), Read(), Write()]),
    )
    await launch_console(agent)   # 输入 exit/quit 或按 Ctrl+D 退出

asyncio.run(main())
```

运行后各环节行为：

| 环节 | 行为 |
| --- | --- |
| 消息输入 | 以 `user>` 提示符读输入，`exit`/`quit`/Ctrl+D 退出 |
| 流式渲染 | 回复文本与思考实时打印，工具调用与结果整块输出 |
| 工具确认 | 逐个询问：`y` 允许一次，`a` 接受建议规则（后续不再问），其余拒绝 |
| 中断 | 流式输出中按 Ctrl+C 中断；确认提示处按 Ctrl+C 终止等待 |

> 注意：`launch_console` **不含会话管理与持久化**，对话状态在 `agent.state` 里、随进程退出而结束。需要多用户、多会话、落库，请走 `08-部署/Agent 服务.md` 那套应用服务。

### 嵌入事件渲染器

自己掌控运行逻辑（多智能体流水线、测试脚本）时，只用 `ConsoleRenderer` 做打印即可，事件如何产生、输入如何处理全由你定：

```python
from bocomagentscope.console import ConsoleRenderer
from bocomagentscope.message import UserMsg

renderer = ConsoleRenderer()
async for event in agent.reply_stream(UserMsg("user", "你好！")):
    renderer.render(event)

final_msg = renderer.last_msg   # 渲染器会累积回一条完整回复消息
```

多智能体顺序发言也能复用同一个渲染器（它按 reply 标识区分归属）：

```python
renderer = ConsoleRenderer()
msg = UserMsg("user", "写一段产品介绍")
for agent in [writer, reviewer]:
    async for event in agent.reply_stream(msg):
        renderer.render(event)
    msg = renderer.last_msg   # 上一个智能体的完整回复作为下一个的输入
```

输出详细程度用 `verbosity` 控制，三档递增：

| 档位 | 显示内容 |
| --- | --- |
| `quiet` | 仅回复文本与错误信息 |
| `default` | 增加思考过程、工具调用与结果、提示块、token 用量、确认提醒 |
| `debug` | 再增加生命周期事件（模型调用开始、回复结束原因等）与工具结果元数据 |

## 三、消息与事件（Message & Event）—— 数据怎么流转

### 先分清两个词

- **消息（Msg）**：一次完整的对话信息——一次用户输入、或一次完整的智能体回复。它是**智能体间通信、上下文持久化**的基本单元，也是前端渲染时的「一个气泡」。
- **事件（Event）**：智能体运行（`reply_stream`）时**逐块吐出的增量**——一个字、一段思考、一次工具调用、一个工具结果。它是**前后端流式传输、人工介入**的基本单元。

一句话：**一堆事件最终能拼成一条消息**；一条消息也可以被拆回成一串事件重放。

### 消息的结构

`Msg` 的核心字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `str` | 唯一消息 ID |
| `name` | `str` | 发送方名称 |
| `role` | `"user" \| "assistant" \| "system"` | 发送方角色 |
| `content` | `list[ContentBlock]` | 有序内容块列表 |
| `metadata` | `dict` | 任意键值元数据 |
| `created_at` / `finished_at` | `str` | 创建 / 完成时间（ISO 8601） |
| `usage` | `Usage` | token 用量（仅 assistant） |

内容由「块（Block）」组成，每块代表一类信息：

| 块类型 | 含义 |
| --- | --- |
| `TextBlock` | 纯文本 |
| `ThinkingBlock` | 模型的思考过程（思维链） |
| `DataBlock` | 二进制数据（图片 / 音频 / 视频，base64 或 URL） |
| `ToolCallBlock` | 工具调用（名称、输入、状态） |
| `ToolResultBlock` | 工具执行结果 |
| `HintBlock` | 提示信息（调度触发、团队消息、后台工具结果等），会转成 user 消息喂给模型 |

> 角色约束（构造时强制）：`user` 消息只能含 `TextBlock`/`DataBlock`；`system` 只能含 `TextBlock`；`assistant` 可含全部类型。

构建消息有三个快捷工厂（自动设好 `role`，字符串会自动包成 `TextBlock`）：

```python
from bocomagentscope.message import UserMsg, AssistantMsg, SystemMsg, TextBlock, DataBlock, Base64Source

user_msg   = UserMsg(name="user", content="这张图片里有什么？")
system_msg = SystemMsg(name="system", content="你是名为 Friday 的 AI 助手。")
assistant_msg = AssistantMsg(name="Friday", content="你好，有什么可以帮你的？")

# 多模态：文本 + 图片
img_msg = UserMsg(name="user", content=[
    TextBlock(text="描述这张图片："),
    DataBlock(source=Base64Source(data="...", media_type="image/png")),
])
```

常用提取方法：

```python
text = msg.get_text_content()                 # 拼接所有文本块
tool_calls = msg.get_content_blocks("tool_call")  # 按类型过滤
if msg.has_content_blocks("tool_result"): ...     # 是否含某类块
```

### 事件：流式传输单元

事件都带 `reply_id`（属于哪条消息），用 `block_id`/`tool_call_id` 关联具体块；同一次 `reply_stream` 的所有事件共享同一 `reply_id`。

所有事件遵循 **start → delta → end** 模式，例如一段文本：

```
TextBlockStartEvent → TextBlockDeltaEvent(×N) → TextBlockEndEvent
```

下面是「事件速查表」，按类别列出常用事件和它们的含义（字段细节可留作需要时再查）：

| 类别 | 事件 | 含义 |
| --- | --- | --- |
| 生命周期 | `ReplyStartEvent` / `ReplyEndEvent` | 回复开始 / 结束 |
| 生命周期 | `ExceedMaxItersEvent` | 达到最大推理-执行轮数 |
| 文本 | `TextBlockStart/Delta/EndEvent` | 文本块开始 / 增量 / 结束 |
| 思考 | `ThinkingBlockStart/Delta/EndEvent` | 思考块开始 / 增量 / 结束 |
| 数据 | `DataBlockStart/Delta/EndEvent` | 图片/音频等数据块开始 / 增量 / 结束 |
| 工具调用 | `ToolCallStart/Delta/EndEvent` | 工具调用开始 / 参数增量 / 参数完成 |
| 工具结果 | `ToolResultStart/TextDelta/DataDelta/EndEvent` | 工具执行与结果（文本/数据增量） |
| 模型调用 | `ModelCallStart/EndEvent` | 模型 API 调用开始 / 结束（含 token 数） |
| 人工介入 | `RequireUserConfirmEvent` / `RequireExternalExecutionEvent` | 暂停等用户确认 / 等外部执行 |
| 人工介入 | `UserConfirmResultEvent` / `ExternalExecutionResultEvent` | 用户输入确认结果 / 外部执行结果 |
| 一次性 | `HintBlockEvent` / `CustomEvent` | 注入提示块 / 自定义信号（任务进度等） |

### 重点：用事件流重建消息

事件和消息是「同一份数据的两种视图」。每个事件都能用 `append_event()` 增量地拼回一条 `Msg`——这意味着**只要有事件流，就能完整还原消息**（前端拿到 SSE 事件流后就是这样重建气泡的）：

```python
from bocomagentscope.message import AssistantMsg, UserMsg
from bocomagentscope.event import ReplyStartEvent, ReplyEndEvent

msg = None
async for event in agent.reply_stream(UserMsg("user", "帮我修复这个 bug")):
    if isinstance(event, ReplyStartEvent):
        msg = AssistantMsg(name=event.name, content=[], id=event.reply_id)
    elif isinstance(event, ReplyEndEvent):
        print("\n[完成]")
    else:
        print(getattr(event, "delta", ""), end="", flush=True)  # 例如 TextBlockDeltaEvent
    if msg is not None:
        msg.append_event(event)   # 始终追加，逐步还原完整消息
# 循环结束后，msg 即为完整回复
```

> 这个设计让部署很灵活：后端把事件流 SSE 推给前端，前端重建并渲染；即使连接中断，从任意检查点重放事件也能精确恢复消息状态。

### 前端（TypeScript）支持

BocomAgentScope 提供 TS 版消息与事件元语，前端用同样的 `appendEvent` 从事件流重建消息：

```bash
pnpm install @bocomagentscope-ai/bocomagentscope
```

```typescript
import { Msg, AssistantMsg, EventType } from "@bocomagentscope-ai/bocomagentscope/message";

let msg: Msg | null = null;
for await (const event of stream) {
    if (event.type === EventType.REPLY_START) {
        msg = new AssistantMsg({ name: event.name, content: [], id: event.reply_id });
    } else {
        msg?.appendEvent(event);
    }
}
```

## 四、计划模式（Planning）—— 让智能体列清单干活

### 这是什么

复杂任务（多步、长链路）如果只靠模型自由发挥，容易遗漏或偏离。BocomAgentScope 内置 4 个工具，让智能体**通过工具调用来维护一份显式、可追踪的任务清单**——任务的创建、查询、更新都走工具，而不是靠模型脑内记。

| 工具 | 作用 | 只读 |
| --- | --- | --- |
| `TaskCreate` | 向清单末尾追加新任务 | 否 |
| `TaskGet` | 按 ID 取单个任务详情（描述、状态、依赖） | 是 |
| `TaskList` | 列出所有任务及其状态、owner、阻塞关系 | 是 |
| `TaskUpdate` | 更新状态/字段/依赖边，也可删除任务 | 否 |

这 4 个都是「状态注入式」工具：运行时把 `AgentState` 注入每次调用，直接读写 `agent.state.tasks_context`。所以任务清单**以智能体为作用域**，并随智能体状态一起持久化。

### 怎么用

像普通内置工具一样注册进 `Toolkit` 即可，无需额外系统提示（工具的 `description` 已写好何时调、怎么用）：

```python
from bocomagentscope.agent import Agent
from bocomagentscope.tool import Toolkit, TaskCreate, TaskGet, TaskList, TaskUpdate

toolkit = Toolkit(tools=[TaskCreate(), TaskGet(), TaskList(), TaskUpdate()])
agent = Agent(
    name="planner",
    system_prompt="You are a planning assistant.",
    model=model,
    toolkit=toolkit,
)
```

### 任务生命周期

典型循环：

1. **登记**：收到新指令，对每个离散步骤调用一次 `TaskCreate`（给一句命令式 `subject` + 详细描述 `description`）。
2. **查看队列**：`TaskList` 返回每个任务一行摘要，挑下一个可做的（通常是 ID 最小、且无未解 `blocked_by` 的 `pending` 任务）。
3. **认领**：开始干活前 `TaskUpdate` 把状态置为 `in_progress`。
4. **取详情**：`TaskGet` 可取完整描述与依赖（描述较长时很有用）。
5. **完成/重规划**：完成则置 `completed`；发现新工作回 `TaskCreate`；无需做则置 `deleted`（硬删除，并自动修正其他任务的依赖边）。

状态流转刻意保持线性：

```
pending → in_progress → completed
                      ↘ deleted（任意状态均可，硬删除）
```

### 表达依赖

任务有两条对称依赖边：`blocks`（本任务完成前不能开始的）和 `blocked_by`（必须先完成的）。用 `TaskUpdate` 的 `add_blocks` / `add_blocked_by` 设置，每次调用**自动维护两端一致**：

```python
await TaskUpdate()(task_id="2", add_blocked_by=["1"], _agent_state=agent.state)
# 结果：task "2".blocked_by == ["1"]，且 task "1".blocks == ["2"]
```

> `TaskList` 会标出仍有未解 `blocked_by` 的任务，`TaskGet` 返回完整依赖边；智能体据此优先做无阻塞的，但**执行层只建议、不强制**——运行时不会阻止模型去做被阻塞的任务。

### 存储与自定义

任务存在 `agent.state.tasks_context`，因此：可随 `agent.state` 一起序列化保存/恢复；默认两个智能体不共享；任何能拿到 `agent.state` 的代码（中间件、应用、评测）都能直接读写。

你也可以在智能体第一次 reply 前，**用代码预置任务**（比如从 Jira / GitHub issues 导入，或评测时注入 ground-truth）：

```python
from bocomagentscope.agent import Agent
from bocomagentscope.state import Task
from bocomagentscope.tool import Toolkit, TaskCreate, TaskGet, TaskList, TaskUpdate

agent = Agent(
    name="planner",
    system_prompt="You are a planning assistant.",
    model=model,
    toolkit=Toolkit(tools=[TaskCreate(), TaskGet(), TaskList(), TaskUpdate()]),
)

# 预置两个有依赖关系的任务
agent.state.tasks_context.tasks.extend([
    Task(id="1", subject="Fetch requirements",
         description="Read README.md and CONTRIBUTING.md.", metadata={"source": "seed"}),
    Task(id="2", subject="Draft plan",
         description="Produce a step-by-step plan.", blocked_by=["1"], metadata={"source": "seed"}),
])
agent.state.tasks_context.tasks[0].blocks.append("2")  # 保持反向边一致

# 想重置：agent.state.tasks_context.tasks.clear()
```

> 手动改 `tasks_context` 时请注意：ID 用数字串（`"1"`/`"2"`…）以便自动分配续上；`blocks` 与 `blocked_by` 要双向一致；`state` 只接受 `pending`/`in_progress`/`completed`（`deleted` 是 `TaskUpdate` 的操作，不是存储状态，手动删除请从列表移除并清理依赖边）。
