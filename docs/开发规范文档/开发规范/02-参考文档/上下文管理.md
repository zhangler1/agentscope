# 上下文管理

> 目标：解决两个问题——长会话上下文爆炸怎么办（压缩/卸载），以及如何让智能体感知运行环境（注入）。
> 另附会话文件通道：文件上传（用户投喂资料）与产物下载（取回智能体产出）的使用方法。

## 创建智能体：填写提示词

创建智能体（`POST /api/agent/`）时即可填写智能体的提示词（`system_prompt`），它作为**基础系统提示**参与每次模型调用的上下文组装（即下文「上下文的三层组装」中的系统提示层）。未填写时使用默认值「你是一个乐于助人的AI助手。」：

```json
{
  "name": "数据分析助手",
  "system_prompt": "你是数据分析助手，负责整理报表并输出到 user-data/outputs/…",
  "context_config": {},
  "react_config": {}
}
```

创建后可随时更新（持久化于 PostgreSQL `system_prompts` 表）：

| 接口                                | 说明                                                     |
| ----------------------------------- | -------------------------------------------------------- |
| `PUT /api/system-prompt/{agent_id}` | 更新指定智能体的提示词（覆盖全局默认）                   |
| `GET /api/system-prompt/{agent_id}` | 获取智能体提示词（未自定义时返回全局默认）               |
| `PUT /api/system-prompt/global`     | 更新全局默认提示词（所有智能体共享，未自定义者自动回退） |

每次模型调用前，框架按「agent 级 `system_prompt` + 技能指令摘要 + 工作区指令」组装基础系统提示，随后 `CustomPromptMiddleware`（`on_system_prompt` transformer）按优先级应用：


## 上下文的三层组装

每次模型调用时，实际输入由三层组装而成：

| 层次     | 内容                                                              |
| -------- | ----------------------------------------------------------------- |
| 系统提示 | 基础 system_prompt + 已注册技能的指令摘要 + 中间件 `on_system_prompt` 的转换结果 |
| 摘要     | 自动压缩生成的结构化摘要（若发生过压缩）                          |
| 上下文   | 历史消息（含工具调用与结果），受压缩/卸载策略约束                 |

## 自动上下文压缩

`ContextConfig` 控制压缩策略：

```python
from agentscope.context import ContextConfig

agent = Agent(
    ...,
    context_config=ContextConfig(
        trigger_ratio=0.8,      # 上下文占用超过窗口 80% 时触发
        reserve_ratio=0.5,      # 压缩后保留约 50% 空间给新内容
        tool_result_limit=5,    # 每个工具最多保留最近 5 条结果
        max_image_num=2,        # 上下文中最多保留 2 张图片
    ),
)
```

自动压缩流程（五步）：

1. 每次推理前检查上下文 token 占用；
2. 占用超过 `trigger_ratio × context_size` 时触发压缩；
3. 调用模型对旧上下文生成**结构化摘要**（已完成任务总览、当前任务、关键发现、待办事项、环境信息）；
4. 用摘要替换旧消息，仅保留最近若干轮原始对话；
5. 超限的工具结果与图片被移除，以 `<<<TRUNCATED>>>` 标记占位（配合卸载器可取回原文）。

**手动压缩**（例如任务阶段切换时）：

```python
from agentscope.message import HintBlock

await agent.compress_context(
    instructions=HintBlock(
        text="压缩时重点保留数据处理任务的进度与关键参数"
    ),
)
```

## 上下文卸载（Offloader）

压缩决定「上下文里留什么」，卸载决定「被移出的内容放哪里」。实现 `Offloader` 协议（两个方法：写入外部存储、按需读回）即可接管：

```python
class S3Offloader:
    """把上下文与工具结果卸载到 S3。"""

    async def save_context(self, state) -> None:
        # 序列化 AgentState 中的历史与工具结果，上传 S3
        ...

    async def load_context(self, state) -> None:
        # 从 S3 读回并还原到 AgentState
        ...


agent = Agent(..., offloader=S3Offloader(bucket="my-agent-context"))
```

工作区自带卸载实现，其磁盘布局（自定义实现可参考复用）：

```text
workspace/
├── sessions/{session_id}/
│   ├── context.jsonl              # 会话上下文逐条记录
│   └── tool_result-{tool_id}.txt  # 超大工具结果的全文
└── data/
    └── {sha256}.png               # 按内容哈希去重的二进制数据
```

最常用的方式是直接把工作区当卸载器：`Agent(..., offloader=workspace)`，见 [沙箱](../06-安全/沙箱.md)。

## 环境感知注入（InjectionConfig）

让智能体「知道现在几点、任务进展、上下文还剩多少」：

```python
from agentscope.context import InjectionConfig

agent = Agent(
    ...,
    injection_config=InjectionConfig(
        inject_time=True,             # 注入当前时间
        inject_tasks=True,            # 注入未完成任务提醒
        inject_context_usage=True,    # 注入上下文用量（提醒智能体节约）
        extra_fields={                # 自定义键值
            "project": "my-app",
            "owner_team": "platform",
        },
        # 自定义模板：必须包含 {runtime_state} 占位符
        template="【运行时状态】\n{runtime_state}\n【项目信息】project=my-app",
    ),
)
```

注入以 `HintBlock` 形式在推理前加入上下文，触发动机包括：会话开始、上下文占用变化、任务状态变更等。

> **警告**：自定义 `template` 若缺少 `{runtime_state}` 占位符，构造时会直接抛错。

三维度注入速查：

| 维度         | 开关                   | 触发时机                 |
| ------------ | ---------------------- | ------------------------ |
| 时间         | `inject_time`          | 会话开始、跨天           |
| 任务         | `inject_tasks`         | 任务创建/状态变更        |
| 上下文用量   | `inject_context_usage` | 占用率变化               |
| 自定义字段   | `extra_fields` + `template` | 每次注入             |

## 沙箱与工作区

**工作区**（Workspace）是智能体执行工具（Bash、文件读写、MCP）的隔离环境，**沙箱**是其在 K8s 上的生产形态。每个会话拥有一个工作目录（workdir），上传文件、交付物、卸载的上下文都落在其中——本节是理解下方文件通道的前提。

### 部署模式

| 模式         | 触发条件                              | 说明                                                         |
| ------------ | ------------------------------------- | ------------------------------------------------------------ |
| 本地模式     | `ADP_K8S_ENABLED=false`               | `LocalWorkspaceManager`，工具直接在宿主机执行，workdir 在 `config.workspace_dir` 下；开发/调试用 |
| K8s 沙箱     | `ADP_K8S_ENABLED=true`（默认）        | 工具在独立 Pod 内执行，与宿主机文件系统隔离；生产形态       |

K8s 沙箱按存储形态又分两种（由 `ADP_K8S_SHARED_PVC_ENABLED` 切换，`WorkspaceManager` 由 `build_k8s_workspace_manager()` 工厂创建）：

| 形态       | 说明                                                           |
| ---------- | -------------------------------------------------------------- |
| 双 PVC     | 每会话独立 Pod + session 级 PVC（RWO），session 间**物理隔离** |
| 共享 PVC   | `SharedPvcK8sWorkspaceManager`，每会话独立 Pod（池 hash 路由复用），agent 级 RWX PVC 共享，`sessions/{session_id}` 子目录隔离；skills/.mcp 位于 agent 级 `shared/` |
| 传统模式   | `K8sWorkspaceManager`，`PER_AGENT` 隔离：每智能体一个 Pod + PVC（RWO），会话排队使用 |

### 工作区目录布局

workdir 内标准布局（共享 PVC 模式由 `_shared_pvc.py` 注入智能体系统提示，自动生效）：

```text
/workspace/
├── shared/                    # 共享 PVC 模式：所有会话共享
│   ├── skills/                #   技能目录
│   └── .mcp                   #   MCP 配置
└── sessions/{session_id}/     # 会话工作目录（workdir）
    ├── data/                  # 卸载的多模态二进制（系统管理）
    ├── sessions/              # 卸载的会话上下文与工具结果（系统管理）
    └── user-data/             # 用户工作目录
        ├── scratch/           # 临时 / 中间文件
        ├── uploads/           # 用户上传文件（文档类自动转 .md）
        └── outputs/           # 最终交付物（产物下载仅暴露此目录）
```

`user-data/` 三目录的职责约定随系统提示注入智能体：

- `scratch/`：临时与中间文件（草稿、构建产物、调试脚本），保持整洁；
- `uploads/`：用户上传文件——文档类自动转同名 `.md`，文本/代码类保留原样，图片固化为 base64；分析文档必须优先读同名 `.md`；
- `outputs/`：任务最终成果（报告、代码、导出文件）**必须**直接写入这里，不要询问用户保存位置。

### 工作区管理（WorkspaceManager）

- 会话创建时按隔离策略生成 `workspace_id`（`PER_SESSION` 随机 UUID / `PER_AGENT` 取 `user::agent` 哈希），持久化于会话记录的 `config.workspace_id`——上传/下载/列表接口据此精确解析会话工作目录，不现场重算；
- 沙箱生命周期由管理器统一管理：空闲超 TTL 回收（默认 1800s）、sweeper 周期扫描（默认 300s）、Pod 池化（`ADP_K8S_MAX_ACTIVE_PODS`、`ADP_K8S_POOL_IDLE_TTL`，按 `hash(session_id) % N` 固定路由）；
- 白名单：`WhitelistWorkspaceManager` 包装层按 agent 过滤挂载的 MCP/工具（`/agents/{id}/tools` 启停接口）。

### host 与沙箱的 IO 边界

host 侧进程无法直接访问 Pod 内的文件系统（PVC 挂载）：

- 所有文件读写经 `workspace.get_backend()`（在沙箱内执行），**绝不在宿主机直接 `Path.mkdir` / `os.open`**；
- 上传时把转换后的 markdown 文本与 ≤20MB 图片的 base64 固化到 SQLite 元数据，host 侧中间件/工具直接查库，避免每次请求都做沙箱 IO；
- `virtual_path`（`/workspace/...` 前缀）是跨 host/沙箱的统一寻址键，不直接用于读取字节。

> 框架层七种工作区后端（Local/Bubblewrap/Docker/E2B/Daytona/K8s/OpenSandbox）的选型、创建与生命周期见 [沙箱](../06-安全/沙箱.md)。

## 文件上传（用户输入）

会话工作区为用户与智能体提供两条文件通道：**上传**（向智能体投喂资料）与**产物下载**（取回智能体产出）。上传文件由 `uploads` 模块统一管理：安全落盘、元数据记录、虚拟路径协议。

### 落盘位置与虚拟路径

- 上传文件一律落在会话 workdir 内的 `user-data/uploads/`，session 隔离由工作区布局天然保证（双 PVC 的 session 级 PVC / 共享 PVC 的 `/workspace/sessions/{id}`）；
- 每个上传文件生成统一虚拟路径 `/workspace/user-data/uploads/{stored_name}`，与内置文件工具（相对 workdir 解析）及下载接口保持同一范式；
- 文档类文件（pdf/docx 等）上传时自动转换出同名 `.md` 并存于同目录；图片（jpg/jpeg/png/webp）固化为 base64 存入元数据，供视觉模型解析。

### 上传接口

所有接口均需携带 `X-User-ID` 请求头（当前为临时身份方案，后续替换为 JWT）。

| 方法   | 路径                        | 说明                                                        |
| ------ | --------------------------- | ----------------------------------------------------------- |
| POST   | `/api/files/upload`         | multipart 上传单个文件（字段：`agent_id`、`session_id`、`file`） |
| GET    | `/api/files/uploads`        | 列举某会话已上传文件（参数：`agent_id`、`session_id`）       |
| GET    | `/api/files/upload/download`| 下载已上传文件（参数：`filename`；`md=true` 取转换后的 `.md`）|
| DELETE | `/api/files/upload`         | 删除上传文件（连同同名 `.md`）                              |
| GET    | `/api/files/limits`         | 查询上传限制（单文件大小、单会话文件数、流式阈值）          |

```bash
# 上传
curl -X POST http://<host>/api/files/upload \
  -H "X-User-ID: u_1001" \
  -F "agent_id=agent_a" -F "session_id=sess_1" \
  -F "file=@manual.pdf"

# 列举
curl "http://<host>/api/files/uploads?agent_id=agent_a&session_id=sess_1" \
  -H "X-User-ID: u_1001"

# 下载原文件 / 转换后的 md
curl -OJ "http://<host>/api/files/upload/download?agent_id=agent_a&session_id=sess_1&filename=manual.pdf" \
  -H "X-User-ID: u_1001"
curl -OJ "http://<host>/api/files/upload/download?agent_id=agent_a&session_id=sess_1&filename=manual.pdf&md=true" \
  -H "X-User-ID: u_1001"
```

上传响应为 `UploadedFile` 元数据（`virtual_path`、`size_bytes`、`converted`、`markdown` 等），其中 `virtual_path` 即智能体侧可读路径。

> **URL 拉取**：在 run 请求的 `custom_params.additional_urls` 中传入 URL 列表，服务端自动下载并保存到会话 uploads 目录（同名文件直接覆盖），行为与手动上传一致。

## 产物下载（智能体输出）

智能体的最终交付物约定写入工作区 `user-data/outputs/`，服务端仅暴露该目录作为交付物通道（不向外部暴露 scratch、代码等中间产物）。

| 方法 | 路径                        | 说明                                                             |
| ---- | --------------------------- | ---------------------------------------------------------------- |
| GET  | `/api/workspace/files`      | 列出会话产出物（仅 `user-data/outputs`，返回 `virtual_path`/`size`/`modified`） |
| GET  | `/api/workspace/files/download` | 按虚拟路径下载产出物（参数：`path`，必须以 `/workspace` 开头） |

```bash
# 列出产物
curl "http://<host>/api/workspace/files?agent_id=agent_a&session_id=sess_1" \
  -H "X-User-ID: u_1001"

# 下载产物
curl -OJ "http://<host>/api/workspace/files/download?agent_id=agent_a&session_id=sess_1&path=/workspace/user-data/outputs/report.pdf" \
  -H "X-User-ID: u_1001"
```

> **约定**：请在系统提示或技能中约束智能体「最终交付物写入 `user-data/outputs/`」，前端据此列出与取回；虚拟路径统一以 `/workspace` 为前缀，解析到 workdir 之外的路径会被拒绝（400/404）。
